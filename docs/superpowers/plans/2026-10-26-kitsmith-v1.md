# kitsmith v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A kit-agnostic MCP server + CLI that makes any coding agent build UI
from a given React kit (antd first): intent search, exact props, recipes,
`validate` (tsc + duplicate detector), and a clickable prototype sandbox.

**Architecture:** One TypeScript npm package. The core (`src/`) knows nothing
about any concrete kit; it loads a per-kit adapter directory by path
(`adapters/antd/` in this repo, others anywhere on disk). An offline index is
extracted from the kit's `.d.ts` with ts-morph and cached per kit version;
MCP tools serve search/props/recipes/guidelines/tokens/validation over stdio.

**Tech Stack:** Node ≥22, TypeScript 5, ts-morph, @modelcontextprotocol/sdk,
zod, minisearch, yaml, gray-matter, jiti, commander, eslint 9 +
typescript-eslint parser, vitest. Sandbox: Vite + React 19 + react-router 7 +
@faker-js/faker. antd major 6 (current: 6.6.8).

**Spec:** `docs/superpowers/specs/2026-10-26-kitsmith-design.md`

**Scope:** spec §9 steps 1–4 (v1). Second kit + benchmark, stage 2 and the
Figma layer get their own plans.

## Global Constraints

- Core code under `src/` must contain no kit names or kit-specific branches (enforced by a test in Task 1).
- Adapters are loaded by filesystem path; built-in ones live in `adapters/`.
- Everything is reachable through MCP **tools**; no feature depends on MCP resources/prompts or on Claude-only skills.
- The decision ladder text is defined once (`src/server/ladder.ts`) and reused in server instructions, tool descriptions and the `AGENTS.md` template.
- No network calls at runtime; no telemetry; kit data never leaves the machine.
- Must work on Windows and macOS/Linux: `path` APIs everywhere, `pathToFileURL` for dynamic imports, no shell-specific commands in code.
- ESM package (`"type": "module"`), `"engines": { "node": ">=22" }`, license MIT.
- Commit messages in English, conventional style; no `Co-Authored-By` or any AI attribution.
- No proprietary kit names, code or design content anywhere in the repo.

## Review Focus

1. **Kit not installed in the target project** (`node_modules/<package>` missing) → a clear `KitNotInstalledError` saying to run `npm install`, never a ts-morph stack trace. Test in Task 3.
2. **Paths with spaces / Windows drive letters** for adapter and project dirs → loading and validation still work. Test in Task 2 (fixture copied to a temp dir with a space in its name).
3. **Russian-language intent queries** ("переключатель") → find the right component via adapter synonyms. Test in Task 4.
4. **`init` on a project that already has `.mcp.json` / `AGENTS.md`** → existing servers and user text preserved, kitsmith section added or replaced idempotently. Test in Task 10.
5. **`validate` given a non-existent file, a file outside the tsconfig, or a project with no `.tsx` files** → a readable message per case, not a crash. Test in Task 7.

## Core types (defined in Tasks 1–2, used everywhere)

```ts
// src/index/types.ts
export interface PropEntry {
  name: string; type: string; required: boolean;
  description?: string; default?: string; deprecated?: string; // message, may be ""
}
export interface ComponentEntry {
  name: string;                 // "Input" or "Input.TextArea"
  description?: string; category?: string; deprecated?: string;
  props: PropEntry[]; subcomponents: string[];  // full names, e.g. ["Input.TextArea"]
  extendsHtmlAttributes: boolean;               // true if props from @types/react were dropped
}
export interface KitIndex {
  kit: string; package: string; version: string; builtAt: string;
  components: ComponentEntry[];
}

// src/adapter/types.ts
export interface AdapterConfig {
  name: string; package: string; typesEntry: string;      // typesEntry relative to the package dir
  deprecated?: { source: "jsdoc"; extra?: string[] };     // extra = component names to mark deprecated
  descriptions?: string;   // yaml: { [Component]: { description, category } }
  synonyms?: string;       // yaml: { [Component]: string[] }
  detectorRules?: string;  // module: default (h: RuleHelpers) => DetectorRule[]
  tokens?: string;         // module: default TokenExtractor
  recipes?: string;        // dir of .md with frontmatter
  guidelines?: string;     // dir of .md with frontmatter
  examples?: string;       // dir of <Component>.tsx usage examples
  allowedExternal?: string[];
  sandbox?: { overlay: string; dependencies: Record<string, string> };
}
export interface DocEntry { slug: string; title: string; intents: string[]; components: string[]; body: string }
export interface DetectorRule { id: string; suggest: string; description: string; rule: import("eslint").Rule.RuleModule }
export type { RuleHelpers } from "../validate/rule-helpers.js"; // type lives next to its implementation
export type TokenExtractor = (ctx: { projectDir: string; requireFromProject: NodeJS.Require }) => Promise<Record<string, unknown>>;
export interface LoadedAdapter {
  dir: string; config: AdapterConfig;
  descriptions: Record<string, { description?: string; category?: string }>;
  synonyms: Record<string, string[]>;
  rules: DetectorRule[]; recipes: DocEntry[]; guidelines: DocEntry[];
  examples: Record<string, string>;
  extractTokens?: TokenExtractor;
}
```

All relative paths in `AdapterConfig` resolve against the adapter dir.
